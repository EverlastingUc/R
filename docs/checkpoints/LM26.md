# LM26 — Direct Preference Optimization

## Objective

Add a preference-alignment stage after supervised fine-tuning (SFT). The policy
starts from an existing Entropy assistant checkpoint and is optimized to assign
higher relative likelihood to a chosen response than a rejected response.

## Dataset format

Training and validation files are UTF-8 JSONL. Each line contains a prompt as
conversation messages and two alternative assistant responses:

```json
{"prompt":[{"role":"system","content":"Be accurate."},{"role":"user","content":"Explain gravity."}],"chosen":"Gravity is the attraction between masses.","rejected":"Gravity is a kind of light."}
```

Use human-reviewed preference labels. Do not treat automatically generated
preferences as ground truth. Keep validation pairs separate from training pairs.

## Training

Run:

```powershell
entropy-preference-train sft-checkpoint.pt preferences-train.jsonl preferences-validation.jsonl --epochs 1 --batch-size 2 --beta 0.1 --output entropy-preference-model.pt
```

The reference policy is a frozen copy of the starting SFT checkpoint. The
trainer applies the sigmoid DPO objective, clips gradients, evaluates held-out
preference loss after each epoch, and saves the best policy checkpoint. The
result remains loadable by the standard Entropy chat inference command.

## Constraints

- DPO is an alignment stage, not a substitute for pretraining or SFT.
- Preference data quality and label consistency directly constrain outcomes.
- The initial implementation uses a frozen in-memory reference model and
  materializes tokenized pairs in memory; large datasets will need streaming.
- It does not implement reward modeling, PPO, tool-use alignment, safety
  certification, or a general preference benchmark.
- No DPO training is claimed until real preference data is supplied and a run
  produces a measured report.
